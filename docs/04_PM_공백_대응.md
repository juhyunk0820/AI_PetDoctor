# 04. PM 중도 퇴사 커버 — 아키텍처로 커뮤니케이션 비용 줄이기

> **TL;DR**
> 프로젝트 중반에 PM이 퇴사하면서 기획 결정권이 사라졌다.
> 프론트엔드 개발자였던 나는 **"역할을 넘어서라도 이 공백을 메워야 출시할 수 있다"** 고 판단했다.
> **도메인 기반 폴더 구조**로 프로젝트를 재편하여 팀 간 커뮤니케이션 비용을 줄였고,
> 결과적으로 PM 공백에도 **6개월 일정 내 양대 스토어 정식 출시**를 달성했다.
>
> 이 경험에서 **"기술적 구조(아키텍처)가 팀의 커뮤니케이션 구조를 결정한다"** 는 콘웨이 법칙을 몸으로 이해했다.

---

## 🎬 상황: 어느 날 갑자기

프로젝트 중반쯤, PM이 개인 사정으로 중도 퇴사했다.
새 PM이 바로 투입되는 상황도 아니었다. 공석이 길어질 가능성이 보였다.

팀은 이런 구성이었다.
- 👤 **PM 1명** (퇴사)
- 🎨 **디자이너 1명**
- 🛠 **백엔드 4~5명** (팀 리드 있음)
- 📱 **프론트엔드 1명 (나)**

PM이 떠난 직후, 가장 먼저 드러난 문제는 **"누가 무엇을 결정하는가"가 모호해졌다**는 것이었다.

## 🚨 PM 공백이 만든 구체적 문제

### 1. 기획 디테일이 충돌하기 시작했다

기획 문서는 있었지만 **빈틈이 많았다**. PM이 있을 땐 "이 경우엔 어떻게 하나요?" 하고 물어보면 즉석에서 결정되었다. 하지만 이제는 그 결정권자가 없었다.

그 결과:
- 프론트(나)와 백엔드가 **같은 기능을 다르게 해석**하기 시작했다
- "로그인 후 어디로 이동해야 하는가" 같은 작은 결정도 답이 없어 지연됨
- 결정을 미룬 채로 개발을 진행하니 나중에 맞물리지 않는 부분이 속출

### 2. 일정 관리가 증발했다

PM이 관리하던 Jira 이슈들의 **우선순위**가 더 이상 조정되지 않았다.
- 급한 작업과 덜 급한 작업의 경계가 흐려짐
- 백엔드 4~5명 사이의 작업 순서 조율도 없어짐
- "이번 주에 무엇을 끝내야 하는가" 가 불명확

### 3. 외부 커뮤니케이션 공백

디자인 변경, 클라이언트사 요청, 법무 검토 등 **프로덕트 외곽 업무**를 받아내던 창구가 사라졌다.

## 🤔 선택의 순간

나는 프론트엔드 단독 담당자였다. 역할 규정상 **"내 일만 하면 되는"** 위치였다.

하지만 이 상황을 방치하면:
- 일정이 미끄러짐 → **양대 스토어 출시 타이밍 놓침**
- 팀 내부 혼란 증폭 → **생산성 전반 저하**
- 클라이언트사 신뢰 하락

역할 경계를 지키는 것이 **장기적으로는 팀에 손해**라는 판단이 섰다.

**"이 모호함을 방치하면 출시가 늦어진다. 내가 일부를 커버하자."**

물론 나도 기획 결정의 최종 책임자는 아니었기에, 팀 리드급과 매번 상의하며 진행했다. 하지만 실무 레벨의 기획 디테일 정리와 일정 트래킹은 내가 맡기로 했다.

## 🏗 해결 전략: 아키텍처로 문제를 풀자

흔한 접근은 **"커뮤니케이션을 더 자주 하자"** 였을 것이다.
- 매일 스탠드업 미팅 추가
- 채팅방 늘리기
- 주간 리뷰 세션 신설

하지만 이건 **커뮤니케이션 비용을 증가시키는 방향**이다. 이미 시간이 모자라서 일정이 미끄러지는 상황에서 회의만 늘리는 건 해결책이 아니었다.

대신 나는 **"커뮤니케이션 자체가 덜 필요한 구조"** 를 만들고 싶었다.

그래서 선택한 것이 **도메인 기반 아키텍처 재편**이었다.

## 🔄 도메인 기반 폴더 구조로 재편

### Before: 기능 단위 폴더 구조

초기에는 일반적인 React Native 구조였다.

```
src/
├── components/
│   ├── Button.tsx
│   ├── Modal.tsx
│   └── ...
├── screens/
│   ├── LoginScreen.tsx
│   ├── HomeScreen.tsx
│   ├── PaymentScreen.tsx
│   ├── ChatScreen.tsx
│   └── ...
├── api/
│   ├── auth.ts
│   ├── payment.ts
│   └── ...
├── store/
└── utils/
```

**문제**: "결제 기능 하나 바꾸려면 5개 폴더를 돌아다녀야" 했다.
백엔드 담당자와 대화할 때도 **"어느 파일을 고쳤는가"** 를 설명하기가 번거로웠다.

### After: 도메인 기반 폴더 구조

서비스를 명확한 도메인으로 나눴다.

```
src/
├── features/
│   ├── auth/           # 인증 도메인
│   │   ├── screens/
│   │   ├── components/
│   │   ├── hooks/
│   │   ├── api/
│   │   └── types.ts
│   │
│   ├── payment/        # 결제 도메인
│   │   ├── screens/
│   │   ├── components/
│   │   ├── hooks/
│   │   ├── api/
│   │   └── types.ts
│   │
│   ├── consultation/   # 상담 도메인 (수의사 채팅)
│   ├── product/        # 상품 도메인 (반려동물 용품)
│   └── pet/            # 반려동물 정보 도메인
│
├── shared/             # 공통 컴포넌트/유틸
└── app/                # 앱 진입점, 라우팅
```

**핵심**: 각 도메인 폴더 안에 **화면, 컴포넌트, 훅, API, 타입이 모두 함께** 있다.

## 💡 이 구조가 팀 협업에 가져온 변화

### 1. "누구와 무엇을 얘기할지"가 명확해졌다

도메인별로 **프론트 담당(나) ↔ 백엔드 담당자**가 **1:1 매칭**되게 정리했다.

| 도메인 | 프론트 | 백엔드 |
|--------|--------|--------|
| auth | 나 | 백엔드 A |
| payment | 나 | 백엔드 B |
| consultation | 나 | 백엔드 C |
| product | 나 | 백엔드 D |

이제 **"이 부분은 누구랑 얘기해야 하나?"** 가 자동으로 답이 나왔다.
팀 전체 채팅방 대신 **도메인별 채팅 스레드**로 나누니 노이즈가 줄었다.

### 2. API 구조와 프론트 구조가 일치했다

백엔드 API도 `/auth/*`, `/payment/*`, `/consultation/*` 등 **도메인별 URL**로 구성되어 있었다.
프론트엔드 폴더 구조도 같은 기준으로 나뉘니, **"같은 지도"** 를 보며 일하게 되었다.

이렇게 되니:
- API 스펙 변경 = 특정 폴더만 영향
- 새 기능 추가 = 해당 도메인 폴더에만 파일 추가
- 버그 수정 = 어디를 봐야 할지 즉시 판단

### 3. 기획 문서의 빈틈 대응이 쉬워졌다

PM이 없어 기획 문서에 빈틈이 많았지만, **도메인별로 쪼개서 보니** 각 도메인 안에서의 빈틈만 메우면 됐다.

내가 한 일:
- 도메인별 **누락된 유스케이스 목록** 작성
- 각 도메인 담당 백엔드와 **미니 스펙 회의** 진행
- 결정사항을 **노션 문서**로 정리하여 팀 전체 공유

### 4. 디자이너와의 협업 방식도 바뀌었다

이전에는 "화면 단위" 로 디자이너와 얘기했다 ("이 화면의 이 버튼 색을...").
이제는 **"사용자 플로우 단위"** 로 얘기하게 됐다. ("결제 도메인의 플로우 전체를 보면서 이 지점에서 이런 상태를 표현해야 합니다.")

이게 의외로 큰 차이였다. 디자이너가 **전체 플로우를 이해한 뒤 디자인**하니 앞뒤 일관성이 훨씬 좋아졌다.

## 🧪 예상 못 한 부수효과

도메인 기반 구조는 PM 공백을 메우기 위해 시작했지만, 그 이상의 효과가 있었다.

### 1. 새 팀원이 투입되었을 때 온보딩이 쉬워졌다

중간에 백엔드 인력이 한 번 교체됐는데, **"결제 도메인만 보세요"** 라고 안내할 수 있었다.
전체 프로젝트를 다 이해할 필요 없이 **해당 도메인만 파악하면** 일을 시작할 수 있었다.

### 2. 도메인 경계가 책임 경계가 됐다

버그가 발생하면 **어느 도메인에서 생긴 버그인가** 가 먼저 판단됐고, 해당 도메인 담당 프론트/백엔드가 집중 대응하는 식으로 **명확한 책임 할당**이 가능해졌다.

### 3. 이 구조가 이후 프로젝트에도 재사용되었다

Wit, Malsami 등 후속 프로젝트에 이 구조를 그대로 가져갔다. **설계 자산이 쌓였다**.

## ⚠️ 놓친 것 / 힘들었던 것

솔직히 모든 게 매끄러웠던 건 아니다.

### 힘들었던 것 1. 리팩토링 비용

이미 기능 단위로 만들어진 코드를 도메인 구조로 옮기는 데 **약 1주일**이 걸렸다.
일정이 타이트한 상황에서 이 결정을 내리는 건 용기가 필요했다. 결과적으론 그 뒤로 절약된 시간이 훨씬 컸지만, 당시에는 불안했다.

### 힘들었던 것 2. 내 역할의 확장 = 내 시간의 희생

기획 디테일 정리, 일정 트래킹, 백엔드 커뮤니케이션까지 떠맡으니 **내가 코드를 쓸 시간이 줄었다**.
주말에도 작업하는 날이 많아졌다.

이건 단기적으로는 어쩔 수 없었지만, 장기적으로는 **"프로젝트 초기에 PM 리스크를 어떻게 대비할 것인가"** 를 고민하게 된 계기가 됐다.

### 놓친 것. 도메인 간 경계가 모호한 케이스들

몇몇 기능은 **두 도메인에 걸쳐있었다**. 예를 들어 "상담 이용권 구매"는 payment 도메인인가 consultation 도메인인가?

이런 경우엔 **주도 도메인(primary domain)** 을 정하고, 다른 도메인은 참조만 하도록 규칙을 세웠다. 이것도 결국 내가 혼자 결정한 것인데, 돌이켜보면 팀 전체와 더 일찍 논의했으면 좋았을 것 같다.

## 🎓 이 경험이 준 3가지 깨달음

### 1. 협업은 "역할 경계를 지키는 것"이 아니다

> **"협업은 역할 경계를 지키는 것이 아니라, 필요하면 역할을 확장해야 한다."**

"나는 프론트엔드 개발자이니 기획은 안 해요"라는 태도는 이 상황에서 통하지 않았다.
팀의 전체 목표(출시) 앞에서, 개인의 역할은 유연하게 조정되어야 한다.

다만 이게 **"무조건 다 떠맡아라"** 라는 뜻은 아니다. **"내가 할 수 있고, 해야만 팀이 굴러가는 것"** 을 구분하는 판단력이 중요하다.

### 2. 콘웨이의 법칙은 진짜다

> "시스템을 설계하는 조직은 그 조직의 커뮤니케이션 구조를 반영하는 시스템을 만들게 된다." — Melvin Conway

그 역도 성립한다. **시스템 아키텍처를 바꾸면 팀의 커뮤니케이션 구조도 바뀐다.**

도메인별 폴더 구조를 만들자, 자연스럽게 도메인별 커뮤니케이션 패턴이 생겼다.
**코드가 팀의 대화 방식을 바꾼 것이다.**

### 3. 위기는 구조를 개선할 기회다

PM 공백이 없었다면 나는 아마 **원래 구조를 계속 끌고 갔을 것이다**.
위기가 오히려 "지금 구조가 정말 최선인가?" 를 묻게 했고, 더 나은 구조를 시도하게 만들었다.

앞으로도 위기 상황에서 **"이게 구조적으로 더 나을 수 있는 신호는 아닐까?"** 를 물어볼 생각이다.
