# 03. Apple IAP 심사 리젝 1개월, 서비스 구조 재설계로 극복

> **TL;DR**
> Apple의 IAP 정책 때문에 앱이 한 달간 반복 리젝됐다.
> 처음엔 기술적 우회를 시도했지만 실패했고, 결국 **서비스 구조 자체를 재설계**해서 통과했다.
> 결과적으로 **수수료 30% → 3% 구조**를 확보하며 양대 스토어 출시에 성공.
>
> 이 경험으로 "개발자는 기술 구현뿐 아니라 비즈니스 정책과 서비스 구조까지 이해해야 한다"는 걸 체감했다.

---

## 🎬 배경: 이상하게 복잡한 결제 구조

AI 펫닥터에는 두 가지 결제 대상이 있었다.

1. 📞 **수의사 상담 이용권** (디지털 재화)
2. 📦 **반려동물 용품** (실물 상품, 택배 발송)

초기 기획은 단순했다.
- 상담 이용권은 **월 구독 형태**로 판매
- 용품은 **일반 이커머스처럼 개별 구매**
- 결제는 **둘 다 Toss Payments 사용**

사업적으로는 이게 당연한 선택이었다.
**Apple IAP는 수수료가 30%**에 달하는 반면, **Toss Payments는 약 3%**.
6개월, 1년 누적하면 **몇 천만 원 단위의 차이**가 나는 문제였다.

## 🚫 첫 번째 심사 제출: 리젝

앱을 App Store에 제출했다. 며칠 후 리젝 통보가 왔다.

사유를 요약하면 이랬다.

> **"디지털 재화(상담 이용권)는 반드시 Apple In-App Purchase(IAP)를 사용해야 합니다.
> 외부 결제 시스템으로 디지털 재화를 판매하는 것은 App Store Review Guidelines 3.1.1 위반입니다."**

Apple의 정책은 명확했다.
- 앱 내에서 사용되는 디지털 재화(구독, 코인, 이용권 등) = **IAP 필수**
- 택배로 발송되는 실물 상품, 앱 외부에서 사용되는 서비스 = **IAP 불필요 (외부 결제 OK)**

우리 서비스는 상담 이용권이 명백히 "앱 내에서 소비되는 디지털 재화"였다.
Apple이 안 된다고 하는 건 타당했다.

## ❌ 첫 번째 시도: UI 수정으로 우회 (실패)

처음엔 "구조를 바꾸지 않고 리젝만 벗어나는 방법"을 찾아봤다.

**시도 1. 결제 버튼 문구 수정**
- "상담권 구매" → "멤버십 가입"
- 구독 설명 UI 간소화

**결과**: 다시 리젝. 사유는 동일. "이름만 바꿨을 뿐 본질이 디지털 재화 구독임."

**시도 2. 결제 플로우를 웹뷰로 이동**
- 앱에서 외부 브라우저로 결제 페이지 이동
- 결제 후 다시 앱으로 복귀

**결과**: 또 리젝. "앱의 핵심 기능(상담)에 연결된 결제는 플로우를 어디로 옮기든 IAP 대상이다."

**시도 3. 결제 자체를 앱 밖에 두기 (웹사이트에서만 구매 가능)**
- 앱에서는 "구독 정보 확인"만 가능하게
- 실제 결제는 웹사이트에서

**결과**: 또 리젝. "앱이 구독의 혜택에 **의존**하고 있다면 IAP를 써야 한다."

## 💡 깨달음: 문제를 다시 정의해야 한다

3번의 리젝 후에 멈춰서 상황을 다시 봤다.

**내가 지금까지 시도한 것들의 공통점은?**
→ 전부 **"기술적 우회"** 였다. "표현만 바꿔서 Apple을 속일 수 있지 않을까?" 하는 접근.

**Apple이 사실 뭐라고 말하는 거지?**
→ 정책 문서를 다시 정독했다. 핵심은 한 줄이었다.

> *"앱의 주요 기능과 연결된 디지털 재화는 IAP로 판매해야 한다."*

**이 한 문장의 뒤집어진 의미는?**
→ **"앱의 주요 기능이 아닌 것에 부수적으로 따라오는 디지털 혜택은 IAP 대상이 아닐 수 있다."**

여기서 출구가 보였다.

## 🔄 재설계: 결제의 "주 대상"을 바꾸기

기획자, 백엔드 팀장과 긴급 회의를 열었다.

내가 제안한 건 이거였다.

> "우리 서비스의 결제 **주 대상**을 '상담 이용권'이 아니라 '실물 상품'으로 재정의하자.
> 실물 상품을 사면 **부가 혜택으로 멤버십(상담 권한)이 딸려오는** 구조로."

쉽게 말하면:

**Before (리젝되는 구조)**
```
[상담 이용권 월 9,900원 구독] ← Apple IAP 필수 (30% 수수료)
```

**After (통과되는 구조)**
```
[반려동물 영양제 월 29,900원 정기 구매] ← 실물 상품, IAP 불필요 (3% 수수료)
  └ 부가 혜택: 이번 달 상담 무제한 이용 ← 부수적 디지털 혜택
```

핵심은 이것이다.
- **결제의 주 대상이 택배로 발송되는 실물 상품**이 됨 (Apple 정책 외)
- **상담은 부가 혜택**이 됨 (결제의 주 대상이 아님)
- 실제로 매달 영양제가 배송되기 때문에 **실물 상품이 주 상품이라는 명분**이 성립

## 🔧 기술 구현 변경 사항

구조를 바꾸기로 결정한 뒤 실제로 프론트엔드에서 바꿔야 할 것들이 많았다.

### 1. 결제 플로우 재구성

**Before**
```
[상담권 선택] → [결제] → [상담 이용 가능]
```

**After**
```
[상품 선택 (영양제 등)] → [멤버십 혜택 안내] → [결제] → [상품 주문 완료 + 상담 권한 활성화]
```

### 2. 상세 페이지 UI 재설계

상세 페이지의 **주요 섹션 순서**가 바뀌었다.
- Before: 상담 서비스 설명이 메인, 상품은 부가
- After: **상품(영양제) 설명이 메인**, 상담은 "이 상품을 구매하시면 함께 제공되는 혜택" 섹션

### 3. 약관 · 결제 정책 텍스트 전면 수정

"구독"이라는 단어를 **모든 화면에서 제거**하고 "정기 배송 + 멤버십"으로 일관되게 교체.

### 4. 구독 해지 UI → 배송 중단 + 멤버십 종료 UI

"구독 해지"는 Apple이 민감해하는 용어였기에, 이것도 **"다음 회차 배송 중단"** 으로 재설계.

### 5. 서버 스키마 재조정

백엔드와 협력하여:
- `subscription` → `recurring_order` (정기 주문)
- `plan` → `product`
- `benefit` 테이블 신규 추가 (멤버십 혜택 관리)

## ✅ 최종 통과

재설계한 구조로 재제출했고, **약 2주 후 통과**.

전체 과정을 정리하면:
- 첫 제출 ~ 통과까지: 약 **1개월**
- 시도 횟수: 리젝 3회 + 구조 재설계 후 1회 통과
- **최종 결과**:
  - ✅ App Store / Play Store 정식 출시
  - ✅ Toss Payments 도입 성공, 수수료 **30% → 3%** 구조 확보
  - ✅ 구조가 오히려 비즈니스적으로 더 건강해짐 (실물 상품 기반 수익 + 리텐션 효과)

## 📚 이 경험에서 배운 3가지

### 1. "기술적 우회"는 정책 문제의 해법이 될 수 없다

처음 3번의 시도는 전부 **"표현만 바꿔서 리뷰어를 속이자"** 는 접근이었다.
돌아보면 **리뷰어는 인간이고, 정책의 의도를 본다**는 걸 간과했다.
이름만 "멤버십"으로 바꾼 구독이 여전히 구독이라는 건 누가 봐도 명백했다.

정책 문제는 **정책의 의도를 존중하면서 해결**해야 한다.

### 2. 개발자의 문제 해결 범위는 "코드" 를 넘어선다

이 문제는 결국 **서비스 구조 설계**, 즉 기획자·사업 담당자의 영역을 건드려야 풀 수 있었다.
개발자가 "나는 주어진 스펙대로 구현만 할게요" 라고만 하면 해결 불가능한 문제였다.

내가 기획자와 백엔드 팀을 적극적으로 설득하러 다닌 것이 결정적이었다.
**개발자도 비즈니스 구조에 개입해야 할 때가 있다.**

### 3. 문제를 재정의하면 해법이 보인다

"어떻게 하면 Apple을 우회할까?" 는 잘못된 질문이었다.
"Apple이 허용하는 구조로 **서비스를 어떻게 재설계할까?**" 가 올바른 질문이었다.

같은 사실도 질문의 프레이밍이 바뀌면 해법이 달라진다.

## 🎯 다음에 적용할 것

**1. 외부 시스템 정책은 개발 시작 전에 깊게 파악한다**
Apple IAP 정책은 훨씬 먼저 알 수 있었다. 리젝을 1달이나 겪고 나서야 제대로 읽었다는 건 **조사 부족**이었다.

**2. 결제/인증 같은 도메인은 기획 단계에 개발자가 끼어야 한다**
"기획이 끝난 뒤 구현만 하는 개발자" 포지션으로는 이런 문제를 조기에 막을 수 없다.
다음 프로젝트에선 **기획 단계부터 정책 리스크를 함께 리뷰**할 것.

**3. "기술적으로 가능한가?" 이전에 "비즈니스적으로 건강한가?" 를 묻는다**
결과적으로 재설계된 구조가 **비즈니스적으로 더 튼튼**했다.
실물 상품이 결제의 주 대상이 되면서 **리텐션, LTV, 재고 관리** 등이 더 명확해졌다.
첫 설계가 놓친 부분을 Apple이 역으로 짚어준 셈.
