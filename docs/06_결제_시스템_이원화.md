# 06. Toss Payments 기반 이원 결제 시스템 설계

> **TL;DR**
> AI 펫닥터에는 **두 종류의 결제**가 있었다: 실물 상품(반려동물 용품)과 디지털 멤버십(수의사 상담 권한).
> Apple IAP 정책 대응을 위해 ([03번 글 참고](03_Apple_IAP_심사_리젝_극복.md)) **두 결제를 하나의 흐름으로 묶는 이원 결제 시스템**을 설계했다.
> 이 글은 그 이원 결제 시스템의 **프론트엔드 구현 관점의 기록**이다.

---

## 🎯 문제 정의

Apple IAP 리젝 대응 끝에 결정된 구조는 다음과 같았다.

```
사용자 결제 1건 = {
  실물 상품 정기 배송 (ex. 반려동물 영양제)
  + 부가 혜택으로 따라오는 멤버십 권한 (ex. 이번 달 수의사 상담 무제한)
}
```

겉보기엔 단순해 보이지만, 프론트엔드 관점에서는 **복잡도가 꽤 높았다**.

### 풀어야 했던 과제

1. **결제 주 대상과 부가 혜택의 UI 표현**
   실물 상품이 "주"이고 멤버십이 "부가"라는 서비스 구조가 UI에서도 명확해야 한다.

2. **결제 성공 후 2가지 상태의 동시 갱신**
   - 사용자의 **주문 내역** (실물 상품)
   - 사용자의 **멤버십 권한** (디지털)
   둘은 서로 다른 API에서 관리되지만, **UI에서는 하나의 결제 결과**처럼 보여야 한다.

3. **멤버십 만료/갱신 처리**
   정기 배송이 취소되면 → 다음 회차 멤버십도 종료.
   결제 실패 → 기존 멤버십 상태 유지.

4. **웹/앱 결제 환경 분기**
   Toss Payments SDK는 **WebView 기반**. RN과의 인터페이스 설계가 필요.

## 🏗 설계: 상태의 "층위" 나누기

설계의 핵심은 **결제 데이터를 몇 개의 층으로 나누는가** 였다.

```
[결제 요청 단계]
  └── 상품 정보 + 사용자 정보 + 선택된 옵션

[결제 실행 단계] (Toss Payments WebView)
  └── 실물 상품 결제 프로세스

[결제 완료 단계]
  ├── 주문 생성 (실물 상품 배송 예약)
  └── 멤버십 활성화 (디지털 혜택 부여)

[결제 후 상태 갱신]
  ├── 사용자 프로필 (멤버십 등급)
  ├── 주문 내역
  └── 멤버십 상세
```

각 단계를 프론트엔드의 **독립적 관심사**로 보고 설계했다.

## 🔄 상태 관리 전략

[2번 글](02_아키텍처_설계.md)에서 쓴 React Query + Zustand 조합이 여기서 특히 빛을 발했다.

### 결제 진행 중 상태 → Zustand

결제 시작부터 완료까지의 **과정 자체**는 앱 내부 상태다.
"현재 어느 단계인가", "선택된 상품이 뭔가", "할인 쿠폰이 적용됐는가" 등.

```ts
// 개념 예시 (실제 코드 아님, NDA 보호)
const usePaymentStore = create((set) => ({
  step: 'idle',          // idle | selecting | confirming | processing | success | failed
  selectedProduct: null,
  appliedCoupon: null,
  setStep: (step) => set({ step }),
  setProduct: (p) => set({ selectedProduct: p }),
  reset: () => set({ step: 'idle', selectedProduct: null, appliedCoupon: null }),
}));
```

### 결제 완료 후 데이터 → React Query

결제가 완료되면 **서버에 있는 여러 데이터가 동시에 바뀐다**.
- 주문 내역
- 사용자 멤버십 등급
- 상담 가능 횟수

이걸 React Query의 **`invalidateQueries`** 로 한 번에 처리했다.

```ts
// 개념 예시
onSuccess: () => {
  queryClient.invalidateQueries({ queryKey: ['user'] });           // 멤버십 등급
  queryClient.invalidateQueries({ queryKey: ['orders'] });          // 주문 내역
  queryClient.invalidateQueries({ queryKey: ['consultations'] });   // 상담 가능 횟수
}
```

서버 쪽에서 트랜잭션이 끝나면, 프론트엔드는 **"이 키들과 관련된 데이터를 모두 최신화하라"** 만 외치면 됐다. 각 데이터가 필요한 화면들은 React Query가 자동으로 리페치해서 최신 상태를 보여줬다.

이게 없었다면 "유저 정보 setState 호출 → 주문 내역 setState 호출 → 상담 내역 setState 호출..." 을 일일이 해야 했을 것이다.

## 📱 UI/UX 설계

### 결제 전 단계: "주 상품 + 혜택" 표현

상품 상세 페이지에서 중요한 건 **실물 상품이 "주"이고 멤버십이 "부가"라는 인상**이었다.

구조 (개념):
```
[상품 이미지 & 설명]           ← 메인, 가장 크게
[가격 정보]
[정기 배송 안내]

─────────────────────
[ 💝 이 상품을 구매하면 함께 받는 혜택 ]   ← 보조 섹션
[ · 이번 달 수의사 상담 무제한 ]
[ · 상담 이용권 3회 추가 ]
```

이 시각적 위계가 중요했다:
- **실물 상품 정보 = 크고 눈에 띄게**
- **멤버십 혜택 = "덤으로 따라오는 것" 으로 느껴지게**

Apple 심사에서도 이 부분을 봤기 때문에, **UI가 서비스 구조를 정확히 반영**하는 게 필수였다.

### 결제 진행 중: WebView 통합

Toss Payments SDK는 WebView 기반이라 RN과 **인터페이스 설계**가 필요했다.

핵심은 **"결제 진행 중 상태를 어떻게 관리할 것인가"** 였다.

접근 방식:
1. RN에서 결제 시작 → WebView로 Toss 페이지 로드
2. 사용자가 WebView 내에서 결제 완료/취소
3. Toss가 `success` 또는 `fail` URL로 리다이렉트
4. RN이 URL 변경을 감지하여 **결제 결과 처리**
5. 서버에 결제 검증 요청 → 성공 시 주문 + 멤버십 동시 처리 확인

WebView 중에는 **Zustand의 `step` 을 `processing`** 으로 유지하여, 사용자가 화면을 이탈해도 상태가 유실되지 않도록 했다.

### 결제 완료: 단일 화면에서 2가지 결과 표현

결제가 완료되면 **"무엇을 샀는지"** 와 **"어떤 혜택을 얻었는지"** 를 함께 보여줘야 했다.

```
✅ 결제가 완료되었습니다

[주문 내역]
- 영양제 1개월 정기 배송 (29,900원)
- 다음 배송일: 2026.05.15

[활성화된 혜택]
- 멤버십 등급: 프리미엄
- 수의사 상담: 이번 달 무제한 가능
- 유효 기간: 2026.05.15까지
```

UX적으로는 이게 **"하나의 경험"** 으로 느껴져야 했지만, 데이터상으로는 서로 다른 두 API에서 왔다. 이 갭을 메우는 게 프론트의 몫이었다.

## ⚠️ 트레이드오프와 어려움

### 어려움 1. 상태 동기화 타이밍

서버에서 **주문 생성**과 **멤버십 활성화**가 별도 트랜잭션이라,
- 주문은 생성됐는데 멤버십이 아직 활성화 안 된 **찰나의 시점** 이 있었다
- 이 때 사용자가 상담 화면으로 가면 **"상담 가능 횟수 0"** 으로 보일 수 있음

**대응**
- 결제 완료 API가 **두 트랜잭션이 모두 완료된 뒤** 성공을 반환하도록 백엔드와 조율
- 프론트에서는 완료 응답을 받은 뒤에만 `invalidateQueries` 호출

백엔드와의 이런 조율은 [PM 공백 상황에서 도메인 기반 폴더 구조](04_PM_공백_대응.md)로 정리한 덕분에 훨씬 수월했다. 결제 도메인 담당 백엔드와 직접 소통하면 됐다.

### 어려움 2. 결제 실패 복구

결제가 실패하면 사용자의 **이전 상태를 복원** 해야 했다.
- 기존 멤버십은 유지
- 장바구니/선택 상태는 유지하여 재시도 가능

Zustand의 `reset()` 대신 **결제 실패용 rollback 액션**을 만들어서, 실패 시 step만 `idle`로 되돌리고 나머지 선택은 유지했다.

### 트레이드오프. WebView 결제의 UX 제약

Toss Payments SDK가 WebView 기반이라 **네이티브 UX가 아니다**.
- 로딩 애니메이션이 WebView 내부로 갇힘
- 키보드 포커싱이 어색할 때가 있음
- 뒤로 가기 제스처 충돌

네이티브 결제로 전환할 수도 있었지만 **구현 비용이 너무 크고**, 6개월 일정 안에 출시해야 했기에 WebView 방식을 유지했다.

다만 주요 접점에서는 **RN 네이티브 UI로 감싸서** UX 단절을 최소화했다.

## 🎓 이 경험이 준 2가지 깨달음

### 1. 결제 시스템 = "상태 관리의 최고 난이도 문제"

결제 플로우 하나를 제대로 만들면 **상태 관리 전반에 대한 이해가 깊어진다**.
왜냐하면 결제에는 **동기/비동기, 서버/클라이언트, 성공/실패, 중간 단계**가 전부 엮여있기 때문이다.

이걸 깔끔하게 풀어내기 위해서 React Query + Zustand 조합의 **진짜 힘**을 처음으로 체감했다.

### 2. 프론트엔드는 **두 데이터를 하나의 경험으로 합치는 사람**이다

결제 도메인에서 느낀 가장 큰 교훈은:
- 백엔드가 데이터를 주고
- 프론트엔드는 그 데이터들을 **사용자가 이해할 수 있는 하나의 경험**으로 구성한다

주문 내역과 멤버십 활성화는 서버 입장에서는 **다른 테이블, 다른 API**지만,
사용자 입장에서는 **"결제 한 번"** 이다.

이 갭을 메우는 게 프론트엔드의 고유한 기여라고 생각한다.

## 🎯 다음에 적용할 것

**1. 결제 같은 복합 도메인은 상태 층위부터 설계**
"결제 중 상태", "결제 완료 상태", "결제 후 데이터" 를 먼저 분리한 뒤 구현에 들어간다.

**2. 결제 도메인은 백엔드와 프론트가 1:1 페어**
이 복잡도는 혼자서 풀기 어렵다. 페어 오너십이 필수.

**3. 결제 실패 시나리오를 먼저 문서화**
성공 플로우만 그리다가 실패 케이스에서 터진다. 실패 케이스 문서화를 **기능 개발 전**에 한다.
