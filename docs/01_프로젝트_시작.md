# 01. 프로젝트 시작과 책임 범위

> **TL;DR**
> 프리랜서 프론트엔드로 참여한 AI 펫닥터 프로젝트는 7-8인 팀에서 **프론트엔드 100% 단독 담당**이었다.
> "앱 출시를 해본 적 없던" 내가 이 책임을 어떻게 받아들였고,
> 어떤 원칙으로 프로젝트를 시작했는지 기록한다.

---

## 📋 프로젝트 배경

| 항목 | 내용 |
|------|------|
| 서비스 | AI 펫닥터 — 반려동물 24시 건강상담 |
| 클라이언트 | 반려동물 헬스케어 스타트업 (NDA) |
| 개발사 | 대모산개발단 (프리랜서 외주 경로) |
| 기간 | 2025.11 - 2026.04 (약 6개월) |
| 팀 구성 | PM 1명, 디자이너 1명, 백엔드 4-5명, 프론트엔드 1명 (나) |
| 내 역할 | 프론트엔드 100% 단독 담당 |

## 🎯 서비스 핵심 가치

반려동물 보호자들은 밤이나 주말에 반려동물이 이상 증상을 보일 때 즉각적인 상담을 받기 어렵다.
오프라인 수의사 상담은 영업시간 제약이 있고 비용도 부담스럽다.

이 서비스는 **AI 이미지 인식으로 1차 스크리닝 → 수의사 실시간 채팅 상담**으로 연결해주는
24시간 상담 플랫폼을 목표로 했다.

## 🤔 프론트엔드 단독 담당을 받아들일 때의 고민

솔직히 처음 프로젝트를 제안받았을 때 두 가지 마음이 있었다.

**부담감**
- 프론트엔드 팀원이 나 한 명. 내가 막히면 프로젝트가 막힌다.
- 앱 스토어 정식 출시를 처음부터 끝까지 담당하는 건 처음.
- Apple IAP, PASS 본인인증 같은 **외부 시스템 연동이 많은 프로젝트**.

**기회**
- 단독 담당이라는 건 동시에 **엔드투엔드 오너십**을 갖는다는 뜻.
- 기술 선택의 자유가 있다 = 내가 원하는 아키텍처를 시도할 수 있다.
- 실제로 사용자에게 도달하는 제품을 만드는 경험.

결국 **기회 쪽이 컸다**. 수많은 프로젝트가 "이런 저런 기능을 만들어봤다"로 끝나는데,
이 프로젝트는 **"실제로 앱 스토어에 출시되어 사용자가 쓴다"** 는 게 달랐다.

## 📐 초기에 세운 3가지 원칙

프로젝트를 시작하면서 스스로 세운 원칙이 있다.

### 원칙 1. "기능"이 아니라 "도메인"으로 생각하자

초기엔 기능 단위로 폴더를 나누려 했다 (`components/`, `screens/`, `utils/` 식).
하지만 서비스가 **결제 / 인증 / 상담 / 상품**이라는 명확한 도메인으로 나뉘어 있다는 걸 깨닫고,
도메인 기반 구조로 가기로 결정했다.

이 결정은 나중에 PM이 중도 퇴사했을 때 [큰 힘이 되었다](04_PM_공백_대응.md).

### 원칙 2. 상태 관리는 "종류"로 분리하자

서버 상태와 클라이언트 상태는 본질이 다르다.
- 서버 상태는 **원격 데이터의 캐시**
- 클라이언트 상태는 **UI와 세션 정보**

이 둘을 같은 도구로 관리하려 하면 반드시 문제가 생긴다는 건 이전 프로젝트에서 이미 배웠다.
그래서 [React Query + Zustand 조합](02_아키텍처_설계.md)을 선택했다.

### 원칙 3. 출시 전까지 일정을 지키는 것이 최우선

"완벽한 아키텍처"는 이상이지만, **일정 내 출시가 더 중요**하다는 걸 인정했다.
모든 결정은 "이게 6개월 일정 안에 출시 가능한가?" 를 기준으로 판단했다.

이 원칙은 나중에 [Apple IAP 대응](03_Apple_IAP_심사_리젝_극복.md)을 할 때도 유효했다.
"기술적으로 우아한 해결책"을 찾기보다 "심사를 통과하는 해결책"을 먼저 찾았다.

## 🚦 시작 직후 마주한 현실

하지만 좋은 원칙을 세웠다고 해서 프로젝트가 순탄했던 건 아니다.

초기 2~3주는 주로 **외부 시스템 연동 조사와 계약 확인**에 시간을 썼다.
- Toss Payments 가맹 계약과 SDK 검토
- PASS 본인인증 발급 절차와 API 스펙
- Apple Developer 계정, Google Play Console 등록

개발을 시작하기 전에 **"이 서비스가 기술적으로 가능한가?"** 를 확인해야 했고,
이 단계에서 뒤에 나올 [Apple IAP 이슈의 씨앗](03_Apple_IAP_심사_리젝_극복.md)이 이미 보였다.

## 💡 이 시점에서 배운 것

프로젝트를 본격적으로 시작하기 전, 단 2~3주의 조사 기간에서 이미 많은 걸 느꼈다.

**1. 개발은 코드만이 아니다**
결제 계약, 심사 정책, 법적 요건 등 **"코드를 짜기 전에 풀어야 할 것들"** 이 더 많을 수 있다.

**2. 단독 담당의 진짜 무게는 "기술 선택의 책임"이다**
아무도 대신 결정해주지 않는다. 매일 수십 개의 작은 선택을 내가 해야 한다.

**3. 초기 원칙이 중반 위기를 구한다**
나중에 PM이 떠났을 때, IAP 리젝이 반복됐을 때, 내가 흔들리지 않았던 건
**초기에 세운 원칙**이 판단 기준이 되어주었기 때문이다.
