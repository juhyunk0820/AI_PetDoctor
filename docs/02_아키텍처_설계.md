# 02. 왜 Redux를 쓰지 않았는가: React Query + Zustand 아키텍처

> **TL;DR**
> 이전 프로젝트에서 모든 상태를 Redux에 밀어넣어본 결과, 서비스가 커질수록 리렌더링 제어가 어렵고 보일러플레이트가 폭증하는 걸 경험했다.
> AI 펫닥터에서는 처음부터 **서버 상태 = React Query / 클라이언트 상태 = Zustand** 로 나눴다.
> 이 글은 그 선택의 이유와 실제 트레이드오프에 대한 기록이다.

---

## 🌱 배경: 이전 프로젝트에서의 실패

2024년 7월, React Native CLI 기반 창업 프로젝트(AI 페어링 앱)를 시작했을 때였다.
팀 분위기상 "Redux = 표준"이라는 인식이 강했고, 그 흐름에 따라 **모든 상태를 Redux 스토어에 올려** 관리했다.

사용자 정보, API 응답, UI 상태(모달 열림 여부, 탭 선택 등)까지 전부 같은 전역 스토어에 넣었다.

초기엔 문제없어 보였다.
하지만 서비스가 커질수록 몇 가지 증상이 나타났다.

- 🔴 **리렌더링 제어가 점점 어려워짐**: 어떤 컴포넌트가 왜 리렌더되는지 추적이 힘들었다.
- 🔴 **보일러플레이트 폭증**: API 하나 추가할 때마다 action, reducer, selector, thunk를 복사/수정.
- 🔴 **캐시 무효화 수동 관리**: 결제 완료 후 유저 정보 갱신 같은 플로우에서 어느 상태를 언제 어떻게 갱신할지를 매번 수동으로 결정.

결정적 순간은 **Wit 프로젝트에서 결제 완료 후 유저 정보가 즉시 갱신되어야 하는 플로우**를 만들 때였다.
"지금 내가 캐시 무효화를 수동으로 처리하려고 하는데, 이게 맞는 설계인가?" 라는 의문이 들었다.

## 🔍 본질 재탐색: 서버 상태와 클라이언트 상태는 다르다

이 질문을 파고들자 결국 한 가지 깨달음에 도달했다.

> **서버 상태와 클라이언트 상태는 본질이 다르다.**

| 구분 | 서버 상태 | 클라이언트 상태 |
|------|-----------|------------------|
| 본질 | 원격 데이터의 **캐시** | UI · 세션 정보 |
| 소유자 | 서버 | 앱 자체 |
| 최신성 | 언젠가 **stale** 해짐 | 항상 **정확** |
| 갱신 방식 | 서버에 재요청 필요 | 직접 업데이트 |
| 예시 | 유저 프로필, 상담 내역, 결제 내역 | 로그인 토큰, 모달 open 여부, 선택된 탭 |

**이 둘을 같은 도구로 다루려 한 것이 근본 문제**였다.
서버 상태의 특성(캐싱, 리페치, 무효화)은 Redux 같은 범용 상태 관리 도구로는 매번 수동으로 구현해야 한다.

그래서 AI 펫닥터에서는 **처음부터** 이 둘을 분리했다.

## 🏗 선택: React Query (TanStack Query) + Zustand

### React Query를 선택한 이유

**1. 캐싱과 무효화가 기본 내장**

서버 상태는 결국 "언제 서버에 다시 물어볼지"가 핵심이다.
React Query는 `queryKey` 기반 캐싱과 `invalidateQueries`를 통한 명시적 무효화가 강력하다.

```ts
// 개념 예시 (일반화된 패턴)
const { data: user } = useQuery({
  queryKey: ['user'],
  queryFn: fetchUser,
});

// 결제 완료 시
await purchaseMembership();
queryClient.invalidateQueries({ queryKey: ['user'] });
// → 자동으로 유저 정보 리페치됨
```

이 패턴 덕분에 결제 완료 → 유저 데이터 즉시 갱신 같은 플로우가 **선언적으로** 처리됐다.

**2. 로딩/에러/백그라운드 리페치 자동 처리**

`isLoading`, `isError`, `data`가 기본으로 제공되니 상태 플래그를 일일이 만들 필요가 없었다.

**3. 결제 내역, 상담 내역 등 갱신 빈번한 데이터가 많았다**

AI 펫닥터는 서비스 특성상 "방금 구매한 것", "방금 상담한 것"을 빠르게 반영해야 했다.
이런 시나리오에서 React Query의 자동 갱신이 큰 힘이 됐다.

### Zustand를 선택한 이유

**1. Redux 대비 극도로 적은 보일러플레이트**

```ts
// 개념 예시
const useAuthStore = create((set) => ({
  token: null,
  user: null,
  login: (token, user) => set({ token, user }),
  logout: () => set({ token: null, user: null }),
}));
```

이게 끝이다. Redux였다면 action 타입, action creator, reducer, selector를 모두 만들어야 했다.

**2. 불필요한 리렌더링 제어가 쉽다**

Zustand는 selector 기반 구독이라 **필요한 값만 구독**할 수 있다.
Context API의 "Provider 아래 모두가 리렌더링되는" 문제를 피할 수 있었다.

**3. 러닝 커브가 낮음**

외부 협력자가 합류하더라도 **30분이면 이해 가능한 수준**.
프로젝트 규모 대비 오버엔지니어링을 피하기 좋았다.

## 🗺 실제 상태 분류 기준

프로젝트 중반에 팀 내부에 공유했던 "이 상태는 어디에 둘까?" 판단 기준이다.

### React Query로 관리한 것
- 유저 프로필 (나이, 이름, 포인트 등)
- 내 반려동물 목록
- 상담 내역, 주문 내역
- 상품 목록, 상품 상세
- 결제 내역

**공통점**: 서버에 있는 데이터. 다른 기기에서도 같은 값. 새로고침하면 최신화 필요.

### Zustand로 관리한 것
- 로그인 토큰 (인증 헤더용)
- 현재 로그인 상태 플래그
- 글로벌 모달 open 여부
- 현재 선택된 반려동물 ID (앱 내 컨텍스트)
- 앱 첫 진입 시 온보딩 표시 여부

**공통점**: 서버와 무관한 앱 내부 상태. 화면 간 공유 필요.

### 그냥 `useState`로 충분했던 것
- 단일 화면 내에서만 쓰는 폼 입력값
- 특정 컴포넌트의 애니메이션 상태
- 바텀시트 열림 여부 (화면 지역)

**원칙**: 컴포넌트를 넘어 공유될 이유가 없으면 지역 상태로.

## ⚖️ 트레이드오프와 아쉬운 점

### 포기한 것 1. Redux DevTools 수준의 디버깅 경험

Redux DevTools는 "시간 여행(time travel) 디버깅"과 액션 히스토리가 강력하다.
Zustand도 `devtools` 미들웨어를 붙이면 기본적인 로깅은 되지만, 수준은 못 따라간다.

**대안**: 민감한 플로우에만 로깅을 명시적으로 추가했다.

### 포기한 것 2. 엄격한 상태 변경 패턴

Redux의 "action을 통해서만 상태 변경" 원칙은 대규모 팀에서 안전망이 된다.
Zustand는 자유도가 높아서 **스토어 안에서 직접 set() 호출**이 가능하고, 실수 여지도 크다.

**대안**: 모든 상태 변경 액션을 스토어 안에 **메서드로 정의**하고, 컴포넌트에서 직접 `set()`을 쓰지 않는 컨벤션을 팀 내 규칙으로 정했다.

### 놓친 것. 테스트 문화 정착은 실패

아키텍처 설계는 잘했지만, 테스트 코드를 꾸준히 쓰는 문화까지는 못 만들었다.
**6개월 일정 압박** 때문에 "테스트는 나중"으로 미룬 것이 반복되어, 결국 본격 도입하지 못했다.

이건 다음 프로젝트에서 반드시 바꿀 것.

## 💭 결정의 회고

이 선택이 옳았다고 확신하는 이유 하나만 꼽자면, **"새 기능 추가 속도가 줄지 않았다"** 는 점이다.

일반적으로 프로젝트 후반으로 갈수록 새 기능 하나 추가하는 비용이 커진다 (기술 부채 때문에).
하지만 이 프로젝트에서는:
- 새 API가 추가되면 → `useQuery` 훅 하나 만들면 끝
- 새 전역 상태가 필요하면 → Zustand 스토어에 필드 하나 추가하면 끝

6개월 내내 "상태 관리 때문에 막힌" 순간이 거의 없었다.

그리고 이 패턴은 **Wit, Malsami 등 이후 모든 프로젝트에 그대로 적용**했다. 재사용 가능한 설계 철학이 된 것이다.
