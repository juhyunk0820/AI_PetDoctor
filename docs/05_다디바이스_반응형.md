# 05. 다디바이스 반응형: 폴드·태블릿·OS 확대 모드

> **TL;DR**
> 한국 스마트폰 시장은 생각보다 훨씬 **기기 파편화**가 심하다.
> 갤럭시 폴드, 태블릿, OS 확대 모드(접근성)까지 대응하면서 **"한 화면을 N개의 디바이스에서 자연스럽게 보이게"** 만드는 여정을 기록한다.
>
> 이 과정에서 가장 크게 배운 건 **"반응형은 화면 단위가 아니라 시스템 단위로 설계해야 한다"** 는 것.

---

## 📱 시작: 이력서에 "반응형 대응"이 한 줄이었던 이유

솔직히 말해서, 처음 프로젝트를 시작할 때 반응형을 그렇게 큰 이슈로 보지 않았다.
React Native는 어차피 `flex` 기반이고, Tailwind 비슷한 유틸리티로 대충 만들면 될 거라 생각했다.

하지만 **실제로 다양한 기기에서 테스트를 시작하자** 예상 못 한 문제들이 터졌다.

## 🚨 대응해야 했던 기기/설정들

| 유형 | 구체 기기/설정 | 화면 특징 |
|------|---------------|-----------|
| 일반 스마트폰 | iPhone 12~15, 갤럭시 S 시리즈 | 표준 (5.5~6.7인치) |
| **갤럭시 폴드 (접힘)** | Z Fold 3/4/5 접힌 상태 | **매우 좁은 세로 비율** (5:20 정도) |
| **갤럭시 폴드 (펼침)** | Z Fold 3/4/5 펼친 상태 | **정사각형에 가까운 큰 화면** |
| 태블릿 | iPad, 갤럭시 탭 | 가로/세로 모두 큼, 회전 지원 |
| **OS 확대 모드** | 접근성 설정의 "큰 글씨" | 시스템 레벨에서 **모든 UI 요소 확대** |

각 기기별로 터진 문제들이 다 달랐다.

## 🔥 실제로 터진 문제들

### Case 1. 갤럭시 폴드 접힌 상태에서 버튼이 화면 밖으로

갤럭시 폴드를 접은 상태는 **세로로 길쭉한** 화면이다. 내가 Figma에서 디자인 받은 건 일반 스마트폰 기준이었는데, 폴드 접힘 상태에서 보니:
- 고정 width로 잡아둔 버튼이 **화면 너비를 초과**
- "다음" 버튼이 **화면 밖으로 밀려나 탭 불가능**
- 모달이 **세로로 너무 길게 늘어나** 스크롤이 필요해짐

### Case 2. 태블릿에서 화면이 너무 여백

태블릿(iPad Pro)에서 실행하면 **스마트폰 UI가 그대로 확대**되어서,
- 버튼이 쓸데없이 크고
- 여백이 너무 많아 **"이 앱은 태블릿용이 아니구나"** 라는 인상
- 특히 리스트 화면이 한 열로만 나와 공간 낭비

### Case 3. OS 확대 모드: 가장 치명적

이게 제일 곤란했다. 갤럭시나 iOS의 **접근성 설정**에서 "화면 확대" 또는 "큰 글씨"를 켜면, **시스템 전체가 1.3~1.5배 확대**된다.

이 상태로 앱을 열면:
- **절대 단위(px)로 지정한 요소들이 UI 구조를 깨뜨림**
- 텍스트가 컨테이너를 삐져나감
- 다단 레이아웃이 **한 단으로 강제 변환**됨
- 어떤 화면에서는 **결제 버튼이 키보드에 가려져 보이지 않음**

시니어 사용자들이 OS 확대 모드를 켜고 쓰는 경우가 많아, **이 이슈는 그냥 넘길 수 없었다**.

## 🛠 접근 방식: 땜질 vs 시스템

처음에는 **땜질식 대응**을 했다.

```
문제 발견 → 해당 화면만 수정 → 다른 화면에서 또 터짐 → 또 수정...
```

한 화면을 고치면 다른 화면에서 새 버그가 생기는 악순환이었다.

결국 방향을 바꿨다.

> **"개별 화면을 고치지 말고, 시스템 레벨 규칙을 만들자."**

## 📐 시스템 설계 원칙 4가지

### 원칙 1. 고정 크기 대신 상대 단위 사용

**Before**
```tsx
<View style={{ width: 300, height: 50 }}>
```

**After**
```tsx
import { Dimensions, useWindowDimensions } from 'react-native';

const { width } = useWindowDimensions();
<View style={{ width: width * 0.8, height: 50 }}>
```

`useWindowDimensions` 훅을 쓴 게 중요했다. `Dimensions.get('window')` 는 **앱 실행 시점의 값만** 반환해서, 폴드를 펼치거나 회전하면 반영이 안 됐다. `useWindowDimensions` 는 **변화에 반응**한다.

### 원칙 2. 화면 너비 기준 브레이크포인트 정의

웹에서는 당연한 브레이크포인트 개념을 RN에서도 도입했다.

```ts
// 개념 예시
const BREAKPOINTS = {
  compact: 360,    // 폴드 접힘 등 매우 좁은 화면
  default: 768,    // 일반 스마트폰
  wide: 1024,      // 태블릿
};

function useDeviceType() {
  const { width } = useWindowDimensions();
  if (width < BREAKPOINTS.compact) return 'compact';
  if (width < BREAKPOINTS.wide) return 'default';
  return 'wide';
}
```

이 훅을 만드니 각 컴포넌트에서 **"폴드에서는 어떻게, 태블릿에서는 어떻게"** 를 선언적으로 작성할 수 있게 됐다.

### 원칙 3. 폰트 크기는 상대값 + 확대 모드 대응

OS 확대 모드 대응을 위해 가장 중요했던 건 **폰트 크기 관리**다.

RN에서 기본 `<Text>` 는 OS 확대 설정을 **자동으로 반영**한다. 하지만 이게 컨테이너를 찢어놓는 주범이기도 했다.

해결 방법은:

1. **단일 위치에서 폰트 스케일 관리**
```ts
// 개념 예시 - typography 시스템
const typography = {
  heading: { fontSize: 24, lineHeight: 32 },
  body: { fontSize: 16, lineHeight: 24 },
  caption: { fontSize: 12, lineHeight: 18 },
};
```

2. **특정 영역은 `allowFontScaling={false}`**
결제 금액, 버튼 라벨 등 **UI 안정성이 중요한 요소**는 시스템 확대를 꺼서 레이아웃 붕괴를 방지.

3. **확대 모드 감지 로직**
```ts
import { PixelRatio } from 'react-native';
const fontScale = PixelRatio.getFontScale();
// fontScale > 1.2 일 때 "확대 모드" 로 판단하여 레이아웃 변형
```

### 원칙 4. 주요 화면은 "기기별 테스트 체크리스트" 로 QA

디자인 시스템을 만들어도 **실제 기기에서 확인**하지 않으면 문제를 놓친다.

주요 플로우(로그인, 결제, 상담)에 대해 **기기별 QA 체크리스트**를 만들어서 출시 전 수동 확인했다.

```
[ ] iPhone 15 (기본)
[ ] iPhone SE (작은 화면)
[ ] Galaxy Z Fold (접힘)
[ ] Galaxy Z Fold (펼침)
[ ] iPad Pro
[ ] OS 확대 모드 ON (갤럭시 + 아이폰 각각)
```

이걸 매 주요 배포 전에 한 바퀴 돌렸다.

## 🎨 구체적 해결 케이스

### 케이스 1: 폴드 접힘 모드에서 버튼 밀림

**해결**
- 모든 버튼을 `flex: 1` 기반 가변 너비로 전환
- 좌우 패딩을 `width * 0.05` 같은 비율 기반으로 설정
- 1개 버튼 배치와 2개 버튼 배치를 브레이크포인트로 분기

### 케이스 2: 태블릿에서 공간 낭비

**해결**
- 태블릿 감지 시 **리스트를 2단 그리드**로 전환
- 모달의 최대 너비를 `Math.min(width * 0.9, 600)` 식으로 제한
- 세로 모드와 가로 모드 양쪽 테스트

### 케이스 3: OS 확대 모드에서 결제 버튼 안 보임

가장 난이도가 높았던 케이스.

**원인 분석**
- 화면 하단 고정 버튼이 `position: absolute` + 하드코딩된 위치
- OS 확대 시 키보드가 화면의 더 큰 영역을 차지하면서 버튼 가려짐

**해결**
- `KeyboardAvoidingView` + **확대 배율에 비례한 bottom 오프셋 계산**
- 확대 모드에서는 **스크롤 가능한 푸터 레이아웃**으로 전환
- 버튼 자체도 `flexWrap` 기반으로 변경하여 글자가 늘어나도 대응

## 💭 회고: 반응형은 시작부터 시스템으로

이 프로젝트에서 반응형에 쏟은 시간은 **전체 일정의 약 15~20%** 였다고 느낀다. 적지 않은 비중이다.

그리고 그 대부분이 **"초기에 제대로 안 설계해서 나중에 수습하는" 시간**이었다.

**만약 처음부터 이랬다면 시간을 절반은 줄일 수 있었을 것이다**:
- 디자인 시스템에 브레이크포인트 규칙 명시
- 디자이너에게 "이 컴포넌트가 `compact` 에서는 어떻게 보이나요?" 를 사전에 질문
- 모든 버튼/모달 컴포넌트를 **반응형 내장** 으로 처음부터 만들기
- QA 체크리스트를 **프로젝트 시작 1주 차에** 작성

## 🎯 다음에 적용할 것

**1. 반응형 규칙은 프로젝트 시작 1주 차에 디자이너와 함께 정의**
"이 서비스는 어떤 기기에서 잘 동작해야 하는가?" 를 스펙으로 박아둔다.

**2. 디자인 시스템에 반응형 변형을 내장**
버튼, 모달, 카드 같은 기본 컴포넌트는 **처음부터 브레이크포인트에 반응**하도록 설계.

**3. 접근성 설정 테스트를 QA 루틴에 포함**
OS 확대 모드는 출시 직전에 처음 체크하면 늦는다. **매 스프린트 마지막에 한 번씩** 확인하는 게 낫다.

**4. 기기 매트릭스를 명시적으로 관리**
"우리는 어떤 기기에 대응하는가?" 를 **회의실 벽에 붙여둘 수준**으로 명확히.
