# 07. 프로젝트 전체 회고와 다음에 적용할 것

> **TL;DR**
> 6개월간의 AI 펫닥터 프로젝트를 돌아보며 스스로에게 남긴 노트다.
> 잘한 것, 잘 못한 것, 다음 프로젝트에서 반드시 바꿀 것을 솔직하게 기록한다.
>
> 이 글은 내 성장을 위한 글이지만, 이 회고를 읽는 사람이 **"이 개발자가 어떻게 생각하는가"** 를 알 수 있기를 바란다.

---

## 📊 프로젝트 요약

| 항목 | 내용 |
|------|------|
| 기간 | 2025.11 - 2026.04 (약 6개월) |
| 역할 | 프론트엔드 100% 단독 담당 (PM 공백 후 기획 일부 겸임) |
| 규모 | 7-8인 팀 |
| 결과 | App Store + Google Play Store 정식 출시 |
| 주요 성과 | Apple IAP 대응으로 수수료 30% → 3% 구조 확보 |

## ✅ 잘했다고 생각하는 것

### 1. 초기 원칙을 세우고 흔들리지 않은 것

프로젝트 시작 시점에 세운 3가지 원칙([01번 글](01_프로젝트_시작.md))이 중반 이후의 판단 기준이 되어줬다.

- "기능이 아닌 도메인으로 생각하자"
- "상태 관리는 종류로 분리하자"
- "일정 내 출시가 최우선"

Apple IAP 리젝이 반복될 때, PM이 퇴사했을 때, 다디바이스 반응형이 무너졌을 때 — **매번 어떤 결정을 내릴지 헷갈렸다**. 그때 이 원칙들이 나침반 역할을 했다.

만약 원칙 없이 시작했다면 각 위기마다 즉흥적인 결정을 했을 것이고, 아마 **일정 안에 출시 못 했을 것**이다.

### 2. "기술적 우회" 대신 "구조 재설계"를 선택한 것

[Apple IAP 대응 경험](03_Apple_IAP_심사_리젝_극복.md)은 이 프로젝트의 하이라이트다.

처음 3번의 리젝은 전부 **"기술적 꼼수로 Apple을 속이려는 시도"** 였고, 모두 실패했다.

네 번째 시도에서 방향을 바꿨다. **"기획자·백엔드를 설득해서 서비스 구조를 재설계하자"**. 이 결정이 결과적으로 수수료 30% → 3% 구조를 확보하게 했다.

**개발자가 코드 바깥의 문제를 푸는 것을 두려워하지 않았던 것**이 가장 잘한 일이라고 생각한다.

### 3. 위기를 기회로 바꾸는 선택

PM 공백은 분명 위기였지만, 이 상황에서 **도메인 기반 아키텍처 재편**을 시도한 것이 결과적으로 팀 전체에 도움이 됐다.

역할 경계를 지키는 것이 아니라 **"지금 팀에 무엇이 필요한가"** 를 묻고 움직였다.
돌이켜보면 이 선택이 **내가 단순 구현자를 넘어 팀에 기여하는 개발자가 되는 전환점**이었다.

### 4. 외부 시스템 연동을 많이 경험한 것

6개월 동안 다룬 외부 시스템:
- Toss Payments
- Apple IAP (결국 포기했지만 학습은 많이 됨)
- PASS 본인인증
- Social Login 4종 (Apple/Kakao/Naver/Google)
- EAS 기반 배포 자동화

외부 시스템 연동은 **"문서 읽기 → 시행착오 → 실제 동작 확인"** 의 사이클을 돌려야 하는데, 이걸 **독립적으로 해낼 수 있게 된 것**이 큰 성장이었다.

## ⚠️ 아쉬웠던 것 / 잘 못했던 것

### 1. 외부 시스템 정책은 더 일찍 파악했어야 했다

Apple IAP 리젝은 **1개월을 통으로 소모**했다. 돌이켜보면 이건 **프로젝트 시작 전 1-2주의 사전 조사**로 막을 수 있었던 문제였다.

- Apple IAP 정책 문서를 처음부터 제대로 읽었어야 함
- "디지털 재화를 외부 결제로 판매 가능한가?" 같은 근본 질문을 기획자와 함께 던졌어야 함

**교훈**: 외부 시스템의 **정책 제약**은 가장 먼저 파악해야 하는 리스크다.

### 2. API 계약을 초기에 못 잡은 것

[에러 처리 전략 문제](README.md#학습된-것들)가 가장 큰 기술 부채였다.

- 백엔드마다 에러 응답 규약이 달랐다 (`200 + null` vs `400 + message`)
- 초기에 합의 안 된 부분이 후반으로 갈수록 확대됨
- 결국 뒤늦게 API별로 에러 처리 전략을 분기하는 **거대 리팩토링**을 해야 했음

**교훈**: API 계약은 **구현 시작 전에 문서화해야 한다**. 특히 에러 케이스가 중요하다.

### 3. 반응형 규칙을 시스템 수준에서 선행 설계 못 한 것

[다디바이스 반응형](05_다디바이스_반응형.md) 대응은 결과적으로는 잘 풀렸지만, **전체 일정의 15-20% 를 소모**했다. 많은 시간이었다.

- 갤럭시 폴드, 태블릿, OS 확대 모드를 **처음부터 대응 대상으로 명시**했어야 함
- 디자인 시스템 레벨에서 브레이크포인트 규칙을 **선행 정의**했어야 함
- 땜질식 대응이 아닌 시스템 설계 관점으로 처음부터 접근했어야 함

**교훈**: 반응형은 "나중에 고치는 것"이 아니라 **설계 단계에서 잡는 것**이다.

### 4. 테스트 문화를 못 만든 것

아키텍처와 설계는 잘 세웠지만, **테스트 코드 작성은 끝까지 정착시키지 못했다**.

- "6개월 일정 내 출시" 라는 압박 때문에 테스트를 계속 미룸
- 수동 QA에만 의존 → 회귀 버그 리스크가 누적됨
- 다음 프로젝트에서 리팩토링하려 해도 **테스트 안전망이 없어 무서움**

**교훈**: 일정 압박이 있어도 **최소한의 테스트**(핵심 도메인 단위 테스트)는 포기하면 안 된다.

### 5. 코드 리뷰 부재로 인한 품질 리스크

프론트엔드 단독 담당의 한계였다.
- 내 코드를 리뷰해줄 사람이 **팀에 없었다**
- CodeRabbit 같은 AI 도구를 썼지만 인간 리뷰어의 깊이를 대체하진 못함
- 내가 놓친 엣지 케이스, 안티패턴이 그대로 프로덕션에 올라갔을 수 있음

**교훈**: 코드 리뷰 문화가 있는 팀에서 일하고 싶다는 갈망이 커졌다.

## 🎯 다음 프로젝트에 적용할 것

### 1. 기획 단계부터 개발자가 깊이 개입

이번 프로젝트에서 가장 크게 느낀 건, **"기획이 끝난 뒤 구현만 하는 개발자"** 가 가진 한계다.

Apple IAP 리스크는 기획 단계에서 잡았어야 했다. 에러 응답 규약도 마찬가지다.

다음 프로젝트에서는 **기획 단계부터 개발자가 적극적으로 개입**하여, **"이 기획이 기술적으로 가능한가 / 어떤 정책 리스크가 있는가"** 를 먼저 확인하는 프로세스를 만들고 싶다.

### 2. 프로젝트 시작 1주차 체크리스트 만들기

이번 경험을 바탕으로 **"프로젝트 시작 1주차에 반드시 해야 할 것들"** 체크리스트를 정리했다:

- [ ] 외부 시스템 **정책 리스크 파악** (결제, 심사, 인증 등)
- [ ] **API 계약 초안** 합의 (에러 케이스 포함)
- [ ] **대응 기기 매트릭스** 정의 (어떤 기기/설정 지원?)
- [ ] **반응형 브레이크포인트** 정의
- [ ] **상태 관리 아키텍처** 원칙 수립 (서버/클라이언트 분리)
- [ ] **폴더 구조** 도메인 기반 설계
- [ ] **테스트 도구 + 최소 커버리지 목표** 설정

다음 프로젝트에서는 이 체크리스트를 **실제로 돌려볼 것**이다.

### 3. 팀 안에서 일하고 싶다

이번 프로젝트에서 프론트엔드 단독 담당이 주는 **오너십의 기쁨**도 느꼈지만, 동시에 **코드 리뷰와 페어 프로그래밍 문화의 부재**가 얼마나 큰 손실인지도 체감했다.

다음 기회에는 **시니어 프론트 개발자가 있는 팀**, 코드 리뷰와 페어 프로그래밍이 일상인 조직에서 일하며 체계적으로 성장하고 싶다.

### 4. 테스트 코드를 진짜로 쓴다

"나중에 추가하자"는 통하지 않는다는 걸 배웠다.

다음 프로젝트에서는 **기능 개발과 동시에 단위 테스트 작성**을 규칙으로 삼을 것이다.
완벽한 커버리지가 아니어도 좋다. **핵심 비즈니스 로직** 만이라도 테스트를 붙여두면, 이후 리팩토링의 자유도가 완전히 달라진다.

## 💭 개인적 회고

### 무엇이 나를 성장시켰나

돌이켜보면 이 6개월 동안 가장 크게 성장한 순간은 **기술적 순간이 아니었다**.

- Apple IAP 대응을 위해 **기획자를 설득하러 가던 순간**
- PM 공백을 보고 **"내가 일부를 떠맡자"** 라고 결정한 순간
- 땜질식 반응형 대응을 멈추고 **"시스템을 다시 짜자"** 라고 판단한 순간

모두 **"역할의 경계를 넘어선 결정의 순간"** 이었다.

기술은 그 다음이었다. 결정을 내리고 나서 기술적 구현을 찾아나갔을 뿐이다.

### 어떤 개발자가 되고 싶은가

이 프로젝트 이후 내가 되고 싶은 개발자는 명확해졌다.

**"문제를 재정의할 줄 아는 개발자"**

- 기술적 우회가 아닌 **구조적 해결**을 선택하는 사람
- 내 역할의 경계를 **팀의 목표 앞에서 유연하게 조정**하는 사람
- 코드를 잘 짜는 것보다 **좋은 질문을 던지는** 사람

이걸 위해서는 더 많이 경험하고, 더 많이 실패하고, 더 많이 배워야 한다.

### 감사한 것

- 이 기회를 준 **클라이언트 회사**에게 감사하다. 신입에 가까운 개발자에게 단독 담당을 맡기는 건 쉬운 결정이 아니었을 것이다.
- 기획을 함께 재설계해준 **기획자**에게 감사하다. IAP 리젝 극복은 그 분 없이는 불가능했다.
- 같이 야근한 **백엔드 팀**에게 감사하다. 특히 결제 도메인 담당자와의 협업은 잊지 못할 경험이다.
